## MoSCoW: named release G1, guidance learning demo and pilot readiness

Must means the intended release cannot fulfill its stated promise without the requirement; Should has a tolerable workaround; Could is optional; Won't is excluded this time. This follows [Agile Business Consortium's MoSCoW guidance](https://www.agilebusiness.org/resource/what-is-moscow-prioritization/). ## RICE: illustrate the inputs without inventing evidence

Formula: **Reach × Impact × Confidence ÷ Effort**, per [Intercom](https://www.intercom.com/blog/rice-simple-prioritization-for-product-managers/). Impact scale 3/2/1/0.5/0.25; effort is total product/design/engineering/content/QA person-months. Mandatory gates and dependencies can override rank.

Worked scenario, **not a forecast**: one hypothetical kitchen has 100 eligible J1 decision episodes in 30 days. Reach is distinct episodes potentially affected during that same 30-day window, not people for one row and transactions for another. Impact means likely improvement in verified correct resolution per affected episode. Confidence below 50% intentionally signals very weak customer evidence. Effort is the incremental work **after the current baseline**, including initial review/setup and early maintenance; ongoing burden is separately measured. Never use zero effort for an already built feature.

Example calculation: F41 = 50 × 2 × 0.20 ÷ 1.0 = 20. This score is a comparison aid, not predicted resolutions, money or waste saved. Reach overlaps between rows, so totals cannot be added. Package scopes also overlap (F03/F24); deduplicate before estimating a release.

Sensitivity: if F41 reaches 20–80 episodes, confidence is 10–30%, and effort 0.5–2 person-months, score spans **2–96** at impact 2. Its numerical rank is unstable. If only 10 episodes benefit from F40, its score falls from 36 to 6. This is why discovery and explicit scope decisions dominate weak early-stage math.

## Reconcile with value versus effort and value versus impact

Existing matrices defined value as problem importance and impact as extent of repeated workflow improvement. They overlap conceptually; neither is measured. Practical current conclusions: current guide/owner, useful states and language are bounded additions to a functioning baseline; weekly projection and complete batch lineage are high-effort connected workflows; an open agent adds unproven complexity. Photo/audio/voice value is task-specific, not guaranteed by popularity.

Build order: documentation → authorized bilingual increment → regression/real-device task comparison → protected pilot readiness → optional improvements selected by evidence. New planning/batch work waits for the branch gate. Revisit weekly during pilot; record changed input, evidence locator and resulting decision. A score change without new evidence is a changed assumption, not new research.
